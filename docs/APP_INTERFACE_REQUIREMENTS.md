## Connected interfaces

| Interface                                  | Extension behavior                                                                                                                                                                                                     |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `raycast_data.json`, schema 3              | Validates producer/session, safe revisions, global check state, full-cohort completion, all three capabilities, target readiness, rows and counts. Global failure remains visible.                                     |
| `vesslo://review-homebrew/v2?payload=…`    | Sends unpadded base64url JSON, request schema 2, and exact targets containing `readinessEvidenceId`. Limits remain 16 targets / 24 KiB payload / 32 KiB URL. Vesslo owns confirmation and execution.                   |
| `raycast_receipts.json`, schema 2 envelope | Reads the fixed private aggregate file. New schema 2 receipt/request records preserve original ordered targets and proof IDs. Retained inner schema 1 records are readable history and are never upgraded or replayed. |
| Older export schema 2 / V1 protocol        | Preserves the existing strict global-ready compatibility path when the older producer advertises V1 review and receipt capabilities. It cannot authorize a schema 3 request or substitute for missing target evidence. |
| Unversioned or unsupported exports         | Unversioned snapshots remain browse-only. Unknown explicit schemas are rejected; an older consumer must not reinterpret schema 3 as schema 2.                                                                          |

Schema 3 requires `homebrewReviewV2`, `homebrewTargetReadinessV1`, and `requestReceiptsV2`. It never falls back to V1 when a capability or proof is absent. `checkPhase`/`checkReason`/`checkedInventoryRevision` preserve the previous global semantics: an unrelated Sparkle failure remains `failed/sourceFailure`, and the globally checked inventory revision is absent. Sparkle, App Store, and generic manual-installer actions continue to require the global-ready gate.

Homebrew additionally requires `completedCheckRevision == checkRevision > 0` and `completedInventoryRevision == inventoryRevision`, valid/fresh export and completion times, a consistent count, and valid current identities. The allowed global phases are `ready` or specifically `failed/sourceFailure`; checking, unverified, partial, interrupted, or changed-cohort states cannot authorize a request. Full-loop completion alone is insufficient.

Every selected app must have one `homebrewReadiness` entry binding its original six-field target identity, `source == homebrew`, publisher session, check revision, and inventory revision. A ready entry contains a UUID `evidenceId`, `checkedAt`, and `expiresAt` with no failure reason. Failed entries use `sourceFailed`; unverified entries use `sourceUnverified`; neither carries a proof UUID or its timestamps. Ready evidence must have a positive lifetime no greater than 900 seconds, `now < expiresAt`, `checkedAt <= now + 30 seconds`, and `checkedAt <= lastUpdateCheckAt + 30 seconds`.

App-owned evidence comes from an actual successful managed Homebrew metadata evaluation in the current check scope. Restored health timestamps or the absence of failure do not create positive evidence. It does not promise a fresh network fetch or successful installation. A selected Homebrew failure invalidates its proof, while unrelated Sparkle failures leave valid Homebrew evidence usable. Polling recomputes checked target counts even when the export file is unchanged so expiry removes UI authority. Count badges describe source evidence; app-path availability and every selected-target check still apply.

## Exact Homebrew handoff

The command preserves the selected snapshot and ordered app UUID/Bundle ID/canonical path/cask/installed version/target version. Schema 3 request targets add the exact `readinessEvidenceId` as a seventh field. Search changes do not change the selection. Submission forces a new export/path read and compares schema/capabilities, session/cohort revisions, each identity/source/action, and the full selected proof fingerprint. Changing a proof's fields with the same UUID is still a change. Expired or changed selected evidence blocks the entire request. A change to an unrelated target's evidence does not invalidate the selection. The command cannot broaden to `update-all`, run Homebrew/mas/Terminal, or fall back to a generic update URL.

The current sender selects `runBrew` / `executableUpdate.homebrew` / source `Brew` only. A Brew-owned manual installer stays review-only; it cannot escape through the generic installer URL. Other existing executable routes require matching source metadata and compare the source set again after rereading. Their generic per-Bundle-ID handoff still does not provide source-pinned execution or a receipt; the new receipt flow is scoped to Homebrew review requests.

Single Homebrew rows and the batch command use the same request review screen. The extension opens the app's review; only Vesslo asks for execution confirmation. The receiver validates the proof UUID against its own authoritative lookup and rechecks the execution boundary; changing public JSON is not permission. Its schema 3 contract rejects V1 requests for new execution and explicitly blocks Homebrew handoff routes requiring Terminal/password/sudo. A successful URL open means waiting for a receipt, not acceptance or completion. Repeat submission of the same selection is suppressed for its 120-second request lifetime within the current extension runtime; the app remains responsible for durable request-ID replay handling and conflict detection, including changed proof IDs or target order.

## Receipt interpretation

The request tracker matches the original request schema/ID/session/revisions/time/source and ordered targets, including each schema 2 target's readiness evidence ID. UUID case and equivalent ISO date instants are normalized for Swift reencoding; identity strings remain exact. Receipt object key ordering is immaterial. A changed proof ID is a different request fingerprint, not an interchangeable success record.

The read-only Homebrew Requests command identifies the current publisher session from either a readable schema 2 or schema 3 export and displays earlier sessions separately. A schema 3 global source failure does not turn a matching V2 receipt into an unverified-session record. Accepted, running, verification pending, verified completion, failure, rejection and cancellation remain distinct. Partial failure displays each target. Missing/malformed/permission-denied/unsafe files or revision conflicts cannot provide current confirmation from cached results. Expired terminal results are history; nonterminal results remain visible after 24 hours.

The aggregate reader accepts supported V1 history and V2 request records, preserving each inner schema and original payload. A schema 2 envelope can contain both kinds; an old schema 1 envelope cannot contain new V2 receipts. V1 records display a read-only legacy notice and are never converted into new target-readiness requests. An unsupported original request schema/source or invalid proof contract makes the aggregate explicitly unreadable instead of being reclassified as success. This compatibility boundary applies to other or future senders.
